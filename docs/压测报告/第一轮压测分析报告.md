四个核心发现：

1. **所有常规场景被"30 秒斜坡"节流，从未打满服务端**——吞吐数字是 JMeter 发压节奏的产物，不是服务端容量（第 3 章，有完整数学证明）
2. **降级场景是全场唯一真饱和点，暴露致命设计缺陷**——Redis 挂掉后每个请求同步等 2 秒超时，Tomcat 200 线程全部被占住，容量公式 `200 ÷ 2.015s ≈ 99 QPS`，与实测 98/107 完美吻合（第 4 章）
3. **三处错误率（1.65% / 0.36% / 9.73%）大概率是压测机自身端口耗尽，不是服务端故障**（第 5 章）
4. **混合场景下读延迟从 8ms 退化到 39ms（5 倍）**——fanout 后台任务与读路径争用资源，这是下一轮调优的切入点（第 6 章）

同时要说的**好消息**：核心链路非常健康。10000 线程瞬时爆发 0 服务端错误、中位数 11ms；发布动态在混合负载下依然稳定 6~11ms（异步 fanout 架构的价值被数据验证了）；点赞 P99 只有 3ms。

## 2. 发现①：常规场景全部被斜坡节流，服务端从未被打满

### 2.1 证明一：吞吐 = 线程 × 循环 ÷ 30

对每一个常规场景做除法验证：

| 测试 | 样本 | 线程×循环÷30 | 实测吞吐 |
|------|------|-------------|---------|
| 写 50×50 | 2500 | 83.3 | 84.64 |
| 写 100×50 | 5000 | 166.7 | 168.01 |
| 写 200×50 | 10000 | 333.3 | 335.89 |
| 赞 100×100 | 10000 | 333.3 | 337.25 |
| 赞 200×100 | 20000 | 666.7 | 672.63 |
| 赞 500×100 | 50000 | 1666.7 | 1689.82 |
| 混 100×50 | 5000 | 166.7 | 168.29 |
| 混 200×50 | 10000 | 333.3 | 335.69 |
| 混 500×50 | 25000 | 833.3 | 838.45 |

**18 个常规梯度里，每一个的吞吐都精确等于"发压节奏"**。这意味着瓶颈在 JMeter 的发压侧：线程把循环跑完就退出，线程主要时间都在"排队等启动"，根本没有持续施压。服务端只是"顺手接了个悠闲的流量"。

### 2.2 证明二：Little's Law 算平均并发

`平均并发 = 吞吐 × 平均响应时间`，算出来的才是服务端真实感受到的并发：

| 测试 | 吞吐 | 平均RT | 服务端平均并发 |
|------|------|--------|---------------|
| 读 10000 | 342 | 22.6ms | **7.7** |
| 写 200 | 336 | 6.2ms | **2.1** |
| 赞 500 | 1690 | 2.5ms | **4.2** |
| 混 500 | 838 | 31.8ms | **26.7** |

也就是说：**所谓"5000/10000 线程压测"，服务端全程平均只有个位数请求在途**。这套配置（30 秒斜坡 + 有限循环）测的是"JMeter 能按什么节奏发请求"，不是"服务端能扛多少"。

### 2.3 那这些测试测出了什么？

- **读场景实际上是"瞬时爆发耐受测试"**：10000 个请求在 30 秒内全部成功（除客户端错误），中位 11ms——冷启动/热点事件冲击下的表现是过关的
- **响应时间是真实有效的**：中位/P90/P95 数据可信（服务端无排队时 RT 就是真实 RT），timeline 中位 8ms、publish 6ms、like 2ms，这几个数字可以写进简历
- **点赞 1690 QPS 是可信的"至少"值**：RT 全程 2~2.5ms 无退化，说明还有大余量
- **唯一无效的是"吞吐上限"**——所有 QPS 数字都只能叫"下限"

## 3. 发现②：降级场景——2 秒超时锁死线程池（本轮压测最有价值的发现）

### 3.1 现象：2015ms 的"整齐划一"

降级 100/1000 线程时：最小 2005、中位 2014/2015、P99 2098/2104、最大 2099/2105。

数据库查询的耗时不可能这么整齐（正常 DB 查询是 5~50ms 的波动分布）。**一个标准差极小、集中在 2015ms 左右的分布，只有一个解释：这是某个超时配置的精确值 + 十几毫秒的 DB 兜底查询。**

### 3.2 定位：`application.yml` 第 51 行

```yaml
spring:
  data:
    redis:
      timeout: 2000ms   # ← Lettuce 命令超时
```

再看 timeline 代码结构：`try { Redis收件箱读取 } catch (Exception e) { 降级DB查询 }`——整个 Redis 块只有**一次** 2 秒超时等待。

所以降级链路是：

```
请求 → Lettuce 对着已死连接等命令超时(2000ms) → 抛异常 → catch → DB 查询(~15ms) → 返回
```

2015ms = 2000ms 超时 + 15ms DB 查询。**分毫不差。**

Redis 停掉后，Lettuce 的自动重连会不断尝试连接失败端口，命令在"等待可用连接"状态中排队，直到撞上 2 秒命令超时——每一个请求都老老实实等满 2 秒。

### 3.3 为什么 5000/10000 线程时恶化到 12s/30s？

**Tomcat 默认最大工作线程 200**（yml 里没配 `server.tomcat.threads.max`，走默认值）。每个请求都要占用一个 Tomcat 线程干等 2 秒：

```
降级容量 = Tomcat线程数 ÷ 单请求耗时 = 200 ÷ 2.015s ≈ 99 QPS
```

验证：

| 线程 | 实测吞吐 | 预测（200÷2.015） |
|------|---------|-------------------|
| 5000 | 98.12 | 99.2 |
| 10000 | 107.48 | 99.2（略高是因为少量请求走了快速失败路径，最小 RT 34ms） |

**完美吻合。** 进阶验证时长：5000 个请求 × 2.03s ÷ 200 线程 = 50.75s，实测 50.9s ✓；10000 × 2.03 ÷ 200 = 101.5s，实测 93s（约 1000 个错误请求提前失败，减少了工作量）✓。

10000 线程时中位数 30.6s、最大 64.7s，就是典型的"线程池满 → 请求排队 → 队列越积越深"雪崩过程。**DB 兜底查询本身根本不是瓶颈，是那 2 秒同步等待把整个线程池锁死了。**

### 3.4 这个发现意味着什么

Redis 宕机（生产环境最常见的中间件故障）发生时：

- 当前设计：**全站 Feed 流容量瞬间跌到 ~100 QPS**，所有用户请求排队 12 秒起步，体感上等于服务宕机
- 你的降级代码逻辑上是对的（能兜住、0 错误），但**降级路径自己把容量杀死了**

### 3.5 修复方案：熔断 + 缩短超时（两级防御）

**第一级：把超时降到 500ms**（治标，容量立刻变 400 QPS）：

```yaml
spring:
  data:
    redis:
      timeout: 500ms
```

**第二级：加简易熔断器**（治本，容量回到 DB 级别）。不引新依赖，用一个健康检查组件：

```java
@Component
public class RedisHealthChecker {

    private final AtomicInteger failures = new AtomicInteger(0);
    private volatile long circuitOpenTime = 0;

    private static final int FAILURE_THRESHOLD = 5;   // 连续失败5次 → 熔断
    private static final long RETRY_AFTER_MS = 5000;  // 每5秒放行一次探测

    private final StringRedisTemplate redisTemplate;

    public RedisHealthChecker(StringRedisTemplate redisTemplate) {
        this.redisTemplate = redisTemplate;
    }

    /** timeline() 入口先问这个：false 就直接走 DB，完全不碰 Redis */
    public boolean tryRedis() {
        if (circuitOpenTime == 0) return true;                    // 正常
        if (System.currentTimeMillis() - circuitOpenTime >= RETRY_AFTER_MS) {
            circuitOpenTime = 0;                                   // 半开：放一个请求去试探
            return true;
        }
        return false;                                             // 熔断中
    }

    public void recordSuccess() { failures.set(0); }

    public void recordFailure() {
        if (failures.incrementAndGet() >= FAILURE_THRESHOLD) {
            circuitOpenTime = System.currentTimeMillis();
        }
    }

    /** 后台每 3 秒主动探测，Redis 恢复后自动闭合 */
    @Scheduled(fixedRate = 3000)
    public void probe() {
        try {
            redisTemplate.opsForValue().get("health:ping");
            recordSuccess();
        } catch (Exception e) {
            recordFailure();
        }
    }
}
```

timeline() 改动（三行）：

```java
public TimelineResult timeline(Long userId, Long maxScore, int size) {
    if (redisHealthChecker.tryRedis()) {          // ← 新增
        try {
            // ...原 Redis 收件箱逻辑...
            redisHealthChecker.recordSuccess();   // ← 新增
        } catch (Exception e) {
            redisHealthChecker.recordFailure();   // ← 新增
            log.warn("Redis 不可用，降级到 DB 查询: {}", e.getMessage());
        }
    }
    return getTimelineFromDatabase(userId, maxScore, size);
}
```

**修复后的行为**：Redis 挂掉 → 前 5 个请求各等 500ms → 熔断打开 → 后续所有请求直接走 DB（~15ms）→ 容量从 99 QPS 恢复到 1000+ QPS（DB 路径 3 条索引查询，Druid 池 300 连接，远不是瓶颈）→ Redis 恢复后探测成功 → 自动回到缓存路径。

### 3.6 降级场景重测预期

| 指标 | 修复前 | 修复后预期 |
|------|--------|-----------|
| 中位 RT | 2015ms / 12311ms（5000线程） | 15~30ms |
| 容量 | 98~107 QPS（锁死） | 1000+ QPS（DB 兜底） |
| 目标 | 500 QPS / <500ms | **可达标** ✅ |

## 4. 发现③：三处错误率，大概率是压测机自己端口耗尽

| 测试 | 错误数 | 错误率 |
|------|--------|--------|
| 读 10000 线程 | 165 | 1.65% |
| 降级 5000 | 18 | 0.36% |
| 降级 10000 | 973 | 9.73% |

注意一个细节：**读 10000 线程时服务端中位数只有 11ms、无排队，服务端没有任何理由出错**。降级 10000 线程里错误请求的响应时间最小只有 1ms（连接都没建立就失败了）——这是**连接层失败**，不是业务/服务端错误。

**假说：Windows 临时端口耗尽（Ephemeral Port Exhaustion）**

- Windows 默认临时端口范围 49152–65535，约 16000 个
- TIME_WAIT 状态持续 2~4 分钟
- 你在同一台机器上连续跑了 18 轮测试，读测试（循环 1 次 = 每线程 1 条连接）累计 17700 条连接，降级测试前又叠加了写/赞/混合约 2000 条
- 降级 10000 线程测试开始时：前一轮 5000 条连接还在 TIME_WAIT + 本轮 10000 条新连接 → 逼近 16000 上限 → 部分连接分配不到端口 → `Address already in use` / connect 失败

时间线完全对得上：读系列第 5 轮（累计 7700 条 TIME_WAIT + 10000 新连接）开始出现 165 个错误；降级系列最后一轮（前面 4 轮残余 + 10000 新连接）错误率飙升到 9.73%。

**验证方法（5 分钟）**：

1. 打开对应 HTML 报告的 **Errors** 面板，看异常文本：
   - `Address already in use` / `ConnectException` / `No buffer space available` → 实锤客户端端口耗尽
   - `Connection refused` → 才需要怀疑服务端
2. 命令行验证：`netstat -an | find /c "TIME_WAIT"`，压测中跑一次，看数字是否逼近 16000

**规避措施**：

```powershell
# 扩大临时端口范围（管理员 PowerShell，改完重启生效）
netsh int ipv4 set dynamicport tcp start=1025 num=64510
```

再加两条压测纪律：

- 大线程测试之间**间隔 2~3 分钟**（等 TIME_WAIT 释放）
- 每轮测试前清空旧的 result.jtl，报告才不会混入上一轮数据

## 5. 发现④：混合场景读延迟退化 5 倍——fanout 后台争用

混合 500 线程时读中位从 8ms 涨到 **39ms**（同梯度写 11ms、赞 3ms 稳如老狗）。而纯读场景 5000 线程时中位也只有 8ms。

原因不难找：混合场景下有持续的发布动作（25000 个请求里 1925 次发布），每次发布触发：

1. FeedPublishService 写 DB + 发 MQ
2. FanoutWorker 消费 → 对每个粉丝做 Redis ZADD（Pipeline）+ 批量写 timeline 表

也就是说读请求的 39ms 里，混入了 fanout 任务对 **Redis、DB 连接池、CPU（同机压测放大了这一点）** 的争用。**发布接口自己反而全程 11ms 没受影响——异步 fanout 架构"把扩散开销从用户请求里摘出去"的设计目标被数据验证了**，这是好素材。

下一轮可以深挖的方向（不急，先把 4.5 的熔断修了）：

- FanoutWorker 消费者并发数 vs Redis pipeline 的争用
- Druid 池 300 连接里 fanout 批量写与读查询的分配
- 同机压测的 CPU 争用干扰（把 JMeter 和服务端分开后此现象可能减弱，先别急着下结论）

## 6. 测试环境局限

1. **JMeter 与被测系统同机**：8 个核要同时跑 JMeter（最多 10000 线程的调度）、Java 应用、MySQL、Redis、RabbitMQ。高线程数时压测机自身就是噪声源（读场景 P99 的 203→404ms 尾部增长，有一部分可能是客户端计时被 CPU 调度干扰）。结论方向可信，精确数值要打折。
2. **10000 JMeter 线程需要调堆**：JMeter 默认 1GB 堆扛不住 10000 线程，改 `jmeter.bat` 里的 `-Xms2g -Xmx4g`，否则客户端 GC 会污染响应时间。
3. **修正后的容量结论要等第二轮重测**。本轮所有"下限值"依然有价值

## 7. 第二轮重测方案（修正方法论）

### 7.1 核心修正：从"斜坡+固定循环"改为"持续施压"

| 参数 | 第一轮（错误） | 第二轮（修正） |
|------|---------------|---------------|
| 循环次数 | 1 / 50 / 100 | **永远（Forever）** |
| 持续时间 | 由循环数决定 | **调度器 Duration = 300s** |
| Ramp-up | 30s（实际节流源） | 30s（只占时长 10%） |
| 线程梯度 | 200~10000 | **50 / 100 / 200 / 400** |
| 模式 | — | CLI 模式 |

原理：循环 Forever + Duration 300s 后，线程跑完一轮立刻发起下一轮，**持续在途施压**，吞吐由服务端能力决定而不是发压节奏。RT 上升 → 单位时间完成循环数下降 → 你能看到真实的"吞吐-延迟"曲线拐点。

### 7.2 每个场景的执行卡

**读场景（重测优先级 ①）**

```
线程组: 200 线程, Ramp-up 30s, 循环 Forever, Duration 300s
CSV: user_ids.csv (10000 用户, 随机顺序)
断言: HTTP 200 + code=200
预热: 正式跑之前先跑一轮 60s 小流量(50线程)，让 JIT/缓存热起来，jtl 删掉再跑正式的
记录: 每个梯度单独目录, 梯度间隔 2 分钟
```

梯度：50 → 100 → 200 → 400。**找到"吞吐不再增长且 RT 开始陡升"的拐点，那个才是容量。**

**写场景（优先级 ②）**：同样配置，`feed_ids.csv`/`user_ids.csv` 参数化，目标确认能否站上 500 QPS。注意观察 FanoutWorker 是否积压（RabbitMQ Management 看队列深度，消费速率应 ≥ 生产速率）。

**降级场景（优先级 ③，修完 4.5 熔断再测）**：直接上 500/1000 线程持续压。预期中位 15~30ms、容量 1000+ QPS。**这一组前后对比数据（99 → 1000+）是整个项目最有说服力的调优故事。**

**混合场景（优先级 ④）**：循环 Forever 模式下用 Throughput Controller 控制 7:2:1 配比（第一轮实际是 10:1:2，写占比偏低，会美化数据）。

### 7.3 环境纪律

- 每轮之间 `netstat -an | find /c "TIME_WAIT"` 确认 < 5000
