## 2. 方法论修正验证：这次测的是真容量

一轮的核心问题是"30s 斜坡 + 有限循环"导致吞吐=发压节奏、服务端并发只有 2~27。本轮三个证据证明问题已解决：

1. **L ≈ 线程数**：8 轮测试的 L（吞吐×平均RT）全部落在 95/190/451/901，与线程数 100/200/500/1000 一一对应——每个 JMeter 线程全程都在干活，发压侧不再是瓶颈。
2. **饱和拐点出现**：读 100→200 线程，吞吐 886.5→881.3（持平），中位 RT 113→230ms（翻倍）——加压不再增产、只增加排队，这是教科书式的饱和信号。混合 500→1000 同样持平（981→987）。
3. **交叉验证**：混合 1000 线程稳态吞吐 1,098 × 平均 RT 0.913s = 1,002 ≈ 1,000 线程。Little's Law 闭合。

## 3. 读接口：880 QPS 饱和——单机混部的天花板，不是架构的天花板

**结论：读链路在这台机器上的饱和容量 ≈ 880 QPS（P99 135ms@100线程，0 错误），未达 2000 目标。**

关键证据是**四场景容量聚集现象**：读 880、写 874、混合 986、（修复后）降级 585——所有场景都聚在同一量级。当不同负载类型的容量收敛到同一数值，说明瓶颈是**共享的全局资源**，而非各链路自身的逻辑。这台 8C16G 上 JMeter（100~1000 线程）+ 应用（200 Tomcat 线程）+ MySQL + Redis + RabbitMQ 挤同样的 8 个核，CPU 先于任何单链路组件饱和。

两个佐证：
- 读 100 线程（并发 95，Tomcat 远未满）平均 RT 107ms；一轮并发 ~8 时中位 8ms。并发 ×12、单请求耗时 ×13，吞吐不升——典型的 CPU 排队特征，而非某个连接池/线程池打满。
- 读 200 线程服务端并发 190 ≈ Tomcat 200 上限，吞吐仍与 100 线程持平——说明即使线程池满了，卡的不是它。

**怎么验证**（下次压测时开着看）：任务管理器/`typeperf "\Processor(_Total)\% Processor Time"` 观察 CPU 是否 ≈100%；若 CPU 未满再查 Redis `info clients` 和 Druid 监控页。分离部署（压测机独立）后读容量预期显著上升，但那需要另一台机器，属于可选动作。

## 4. 写接口与混合场景

### 4.1 写：874 QPS，目标 500 的 1.75 倍 ✅

100 线程打满 874 QPS（P99 172ms）；200 线程回落到 786（−10%）、P99 320ms、max 746ms。回落与 MISCONF 故障窗口（§6）时间相关：fanout 消费失败无限重入队、MQ 堆积、重试风暴消耗资源，都是嫌疑因素。**容量口径取 874。**

### 4.2 混合：986 QPS @ 7:2:1，0 错误

500 与 1000 线程吞吐持平（981/987）→ 饱和。分接口：读 691、写 197、赞 98 QPS。
代价是排队延迟：1000 线程时读中位 1,076ms、P99 1.55s——**这是超过容量后继续加压的必然排队代价，不是容量数字**。引用混合数据时用 500 线程那轮（读中位 568ms）更体面。
对比一轮混合（读中位 39ms 但只打了 838 QPS 下限）：本轮读中位升高的本质是"真打满了"，属于预期行为。

## 5. 降级场景：核心故事成立，一个指标未达

### 5.1 熔断器生效的证据链（三条）

1. **min RT = 9ms / 16ms**：有请求个位数毫秒完成——它们完全绕过了 Redis（若仍在等超时，下限应是 500ms+）。一轮的 min 是 2005ms（全员等超时），本轮 min 9ms，行为质变。
2. **RT 分布失去"超时指纹"**：一轮降级中位精确钉在 2032ms（2000ms 超时+DB）；本轮中位 1,677ms、min 9ms、max 2,242ms，分布宽且连续——是排队+服务的形态，不再有超时悬崖。
3. **无队列雪崩**：一轮 5000/10000 线程下中位 12.3s/30.6s、最大 64.7s；本轮 1000 线程最大仅 2.24s。**尾延迟收敛 29 倍**——熔断 + 超时下调把"故障放大器"拆掉了。

### 5.2 容量：99 → 585 QPS（5.9 倍），达标 ✅

一轮饱和点 98~107 QPS（200 线程 ÷ 2.015s）；本轮 1000 线程 585 QPS（稳态 ~653）。

而且本轮数据可以**完整反解出服务端模型**（Little's Law + Tomcat 线程池，两个等式两条数据自洽）：

```
稳态吞吐 λ = Tomcat线程数 ÷ 单请求服务时间 = 200 ÷ 0.306s = 653 QPS
客户端 RT = 服务时间 + 排队时间 = 0.306 + (800÷653) = 1.53s ≈ 实测均值 1.537s ✓
```

即：**降级路径每个请求在服务端真实耗时 ~306ms**（DB 兜底多查 + 200 并发下的 MySQL 竞争），Tomcat 200 线程全部干活，~800 个请求在 TCP 积压队列排队。模型与实测误差 <1%。

### 5.3 RT < 500ms 目标未达：差 3.4 倍，原因和路径都清楚

中位 1.68s = 服务时间 0.31s + 积压排队 1.22s。要达标得同时做两件事：
1. **压低服务时间**（治本）：降级兜底路径加 Caffeine 本地缓存（作者信息、feed 详情短 TTL——Redis 挂了本地缓存还活着，命中率决定兜底成本）；`EXPLAIN` 检查兜底 SQL 的索引覆盖；Druid 慢 SQL 日志（已配 1000ms 阈值）看真实耗时分布。
2. **控制积压**：过载时快速失败（返回降级提示页）比无限排队体验好——这是限流的活儿，可作为下一步演进。

### 5.4 异常点：500 线程只有 268 QPS（1000 线程反而 585）

按 5.2 的模型反推，500 线程轮的单请求服务时间 ~0.67s，是 1000 线程轮的 2.2 倍——**负载更轻反而更慢**。两个假说：
1. **冷缓存**（主嫌疑）：降级是唯一走 timeline 表全量 DB 查询的场景，此前的读/写/混合测试都在打 Redis 和 insert，timeline 表的随机读页早被挤出 InnoDB buffer pool。第一轮降级测试（500 线程）在冷页上做 Windows 磁盘随机读；跑完 300s 后 buffer pool 热了，紧跟着的 1000 线程轮自然快。
2. **后台重试风暴**（次嫌疑）：MISCONF 窗口失败的 fanout 消息在无限重入队（§6.2），每轮重试都打一次 DB + 打一行全堆栈 ERROR 日志。

验证方法（10 分钟）：重启后连跑两轮 500 线程降级，若第二轮显著快于第一轮 → 冷缓存实锤。这不影响简历结论（585 是保守取值）。

## 6. 新问题一：MISCONF——写测中 Redis 拒绝写入

### 6.1 报错解读

日志链路：`FanoutWorker 写扩散失败 → RedisConnectionFailureException → 根因 RedisCommandExecutionException: MISCONF`。

```
写入量大 → 触发 RDB 自动快照（BGSAVE）→ Windows 上 fork 模拟实现失败/磁盘写不动
→ stop-writes-on-bgsave-error=yes（默认）→ Redis 拒绝所有写命令 → ZADD 全军覆没
```

这是 **Windows 版 Redis 的经典坑**：Linux 的 fork 是写时复制（COW），几乎零成本；Windows 的 fork 模拟在高写入+内存压力下会失败。生产环境 Linux 上基本不会遇到。

### 6.2 连带影响比报错本身更重要

1. **写吞吐回落**：写 200 线程比 100 线程低 10%，MISCONF 引发的消费失败堆积是嫌疑之一。
2. **数据一致性窗口**：MISCONF 期间发布的动态**没进粉丝收件箱**。注意这比"Redis 挂了"更隐蔽——Redis 活着、读路径不会兜底查库，数据就是单纯缺失，用户刷不到这些动态。**修复前跑的 like_count/收件箱审计会被这个窗口污染，修完要重跑。**
3. **无限重入队风暴**：FanoutWorker 的 `catch → basicNack(requeue=true)` 没有重试上限（yml 里的 spring-retry max-attempts=3 实际被绕过了——异常在方法体内被 catch 吞掉，永远到不了重试拦截器）。Redis 不可用期间，消息无限循环：每轮都查一次粉丝列表（DB）+ 打一行全堆栈 ERROR。这是资源黑洞 + 日志洪水，也是 §5.4 假说 2 的来源。

### 6.3 修复

```bash
# 压测环境（推荐）：关掉 RDB 自动快照，重启 Redis 后执行，写入配置文件持久化
redis-cli config set save ""
# 或者：不让 BGSAVE 失败阻塞写入（有丢最近快照的风险，仅测试用）
redis-cli config set stop-writes-on-bgsave-error no
```

Linux 部署无此问题； Windows下可 maxmemory 控制与 AOF everysec 替代方案。

### 6.4 FanoutWorker 重试改造（P1，真正的代码债）

```java
// 现状：异常 → nack(requeue=true) → 无限循环
// 改造：失败计数进消息头，超过阈值进死信队列，由定时任务补偿重放
catch (Exception e) {
    Long retryCount = message.getMessageProperties().getHeaders().containsKey("x-retry-count")
            ? (Long) message.getMessageProperties().getHeader("x-retry-count") : 0L;
    if (retryCount >= 3) {
        log.error("写扩散重试耗尽，转入死信队列: feedId={}", feedId, e);
        channel.basicNack(deliveryTag, false, false); // requeue=false + 队列绑定 DLX
    } else {
        // 重发一条带 x-retry-count+1 的新消息（或 basicReject 后由 DLX 循环队列处理）
    }
}
```

FANOUT_QUEUE 声明时绑定死信交换机；补偿 Job 定时扫描死信重放。这一条改造 + "Redis 挂掉时 fanout 怎么保证不丢"是面试高频追问，值得做实。
